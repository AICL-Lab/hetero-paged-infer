# 证据与边界

## 已实现内容

当前仓库已经实现了一个推理引擎的控制平面形状：有具体的 `InferenceEngine`、区分 pending/prefill/decode 的 `Scheduler`、带分页块分配的 `KVCacheManager`、批执行管线、配置校验，以及覆盖混合请求流程和内存压力场景的集成测试。

仓库也明确暴露了未来生产实现的接缝，而不是把未来工作藏起来。`GPUExecutorTrait` 定义了执行器边界，decode graph capture 在接口层已经被建模，整个引擎结构允许未来替换执行器，而不需要推翻调度器或 KV Cache 的整体设计。

## 已模拟或占位的部分

当前执行器是 `MockGPUExecutor`，并不是真实 CUDA 后端。它会模拟执行过程、校验批次约束，并为测试生成确定性的 token。所谓 CUDA graph capture 目前也是接口与 mock 状态层面的表达，不是真正捕获并重放 GPU 图。

因此，凡是依赖 kernel 质量、显存带宽、融合注意力实现或 GPU occupancy 的结论，都应视为未来工作。现在已经真实存在的是架构骨架，不是完整的生产 GPU 路径。

## 哪些结论已有测试或测量支撑

当前项目里最强的“已测量”结论，其实是正确性与结构行为层面的结论：

- 请求可以按 pending → prefill → decode → completed 的状态流转，
- 连续批处理可以在已有请求 decode 时接纳新工作，
- 内存压力会触发准入门控，而不是让系统直接崩溃，
- KV Cache 资源通过显式块计数进行分配与释放，
- 配置和请求参数会被提前校验并拒绝非法输入。

这些结论由现有 Rust 单元测试、集成测试，以及文档站点构建成功共同支撑。它们证明的是“系统结构正在工作”，不是“GPU 性能已经被最终证明”。

## 哪些结论属于估计或继承自参考文献

关于分页式 KV Cache 普遍能降低碎片、连续批处理普遍能提升加速器利用率这类论点，主要来自已有论文和参考系统，而不是仅靠本仓库单独证明。换句话说，Hetero-Paged-Infer 继承了这些成熟设计动机，但不能把“继承来的架构常识”误写成“当前仓库已经在本地完整测得的性能事实”。

在真实 CUDA 后端和完整测量体系落地之前，这些优势更适合被表述为“有充分文献与工程先例支持的预期”，而不是“已经在本项目中最终坐实的 benchmark 结论”。

## 距离生产可信度仍需补齐的内容

在“当前代码可讲清楚”与“具备生产可信度”之间，仍然至少隔着几步关键工作：

1. 真实 CUDA 执行器，以及真实 attention / decode kernel，
2. 基于代表性硬件和模型的端到端 benchmark，
3. 比当前架构骨架更完整的 serving/runtime 强化，
4. 面向延迟、内存和失败行为的可观测性补强，
5. 证明文档中的调度与内存结论在真实 GPU 执行下仍然成立。

简单说：项目已经证明“架构是认真设计过的”，但还没有证明“GPU 实现已经具备生产级可信度”。这条边界应该在整份白皮书里持续保持清晰。
