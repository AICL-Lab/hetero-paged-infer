# 吞吐量

本页说明当前到底有哪些吞吐证据，以及哪些表述只能被视为模拟结果或外部继承结论。

::: warning 口径说明
本页将结论分成三类：
1. 本仓库已测得
2. 基于 mock executor 的模拟结果
3. 来自外部论文或参考项目的结论
:::

## 本仓库已测得

### 当前真实被基准覆盖的内容

- `cargo bench` 会测量 `engine_step`、`batch_processing/{1,4,8,16,32}` 以及调度器相关操作。
- 这些基准跑的是仓库内部代码路径，因此适合比较本项目内部的调度与编排开销。

### 这些吞吐测量目前**不**代表什么

- 它们并不等价于生产级 GPU tokens/sec。
- 默认引擎使用的是 `MockGPUExecutor`：它会校验 batch 形状、生成确定性 token，但不会运行 CUDA 内核。
- 因此，本页若直接给出绝对 tokens/sec 数字，会夸大仓库已经证明的范围。

## 基于 mock executor 的模拟结果

- `tests/integration_tests.rs` 包含连续批处理测试：当第一个请求进入 decode 后，再插入第二个请求。
- 调度器实现采用“decode 优先，再用剩余容量填充 prefill”的策略，因此可以在模拟环境中观察到混合批行为。
- 这支持“调度器是围绕利用率组织的”这一说法，但在接入真实内核前，它仍然只是模拟结论。

## 来自外部论文或参考项目的结论

- “连续批处理通常比静态批处理吞吐更高”这一更广泛的说法，来自 Orca、vLLM 等系统。
- 这些论文解释了*为什么*这种设计有前景，但并不能自动变成本仓库已经实现的精确提升幅度。

## 读者现在应该如何理解

| 说法 | 类别 | 安全解读方式 |
|------|------|--------------|
| 批处理代码路径在多个 batch size 下都能被基准覆盖 | 本仓库已测得 | 软件栈已经对多种 batch 配置做过基准 |
| prefill/decode 混合调度有望优于朴素静态执行 | 基于 mock executor 的模拟结果 | 调度形状是合理的，但硬件证据还未完成 |
| 连续批处理可以带来较大生产吞吐提升 | 来自外部论文或参考项目的结论 | 这是先验工作，不是本仓库本地 benchmark |
