# 设计原则

## 问题

现代推理引擎必须同时协调请求生命周期、内存管理和执行边界。如果这些关注点被揉在一起，代码会很快失去可解释性：调度器开始顺带拥有内存策略，执行器泄漏服务层假设，读者也很难分清楚哪些结论来自当前实现，哪些只是未来优化的设想。

因此，Hetero-Paged-Infer 把“先把系统边界设计清楚”当作第一问题。它要回答的不只是“下一个 token 怎么生成”，还包括“当分页式 KV Cache、连续批处理和未来 GPU 专用化需要一起演进时，整个系统如何仍然可理解、可验证、可替换”。

## 设计选择

项目采用控制平面 / 数据平面的拆分思路。Rust 引擎负责请求校验、分词、调度、KV Cache 元数据和批次组装；真正的执行则放在 `GPUExecutorTrait` 后面，因此今天可以接 `MockGPUExecutor`，未来也可以替换成 CUDA 后端，而不需要推翻外层编排逻辑。

这个选择让项目即使在最终 GPU 路径尚未完成时，也已经具备“工程形状”。`InferenceEngine` 是对服务层暴露的边界，`Scheduler` 负责准入与阶段流转，`KVCacheManager` 负责分页内存元数据，执行管线则是硬件相关逻辑接入的位置。

## 权衡

这种结构的好处是清晰。组件职责明确，测试可以分别针对调度与内存不变量，未来 CUDA 工作也有清楚的落点。它也让文档能保持诚实：项目可以精确描述当前行为，而不必把 mock executor 包装成已经完成的生产 kernel 栈。

代价是，抽象本身不会自动带来性能。trait 边界和干净的主循环只有在未来真实后端能在硬件压力下兑现同样假设时才有最终价值。在那之前，这个项目的“架构完成度”会强于“最终吞吐故事”；而 Hetero-Paged-Infer 选择把这件事明确说出来，而不是掩盖它。

## 当前实现状态

今天，系统结构层面的关键部件都已经存在：引擎构建、请求提交、调度状态流转、分页式 KV 分配，以及覆盖混合执行场景的 Rust 测试都已经在仓库里落地。执行器边界同样真实存在，但默认后端仍然是 `MockGPUExecutor`。

因此，本页应被理解为“仓库已经编码进去的系统形状说明”，而不是“CUDA 生产路径已经完工”的证明。更细的决策级展开可继续阅读 [PagedAttention](./paged-attention) 与 [连续批处理](./continuous-batching)。
