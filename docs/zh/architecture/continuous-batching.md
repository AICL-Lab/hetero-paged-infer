# 连续批处理

## 问题

静态批处理的问题在于：只要不同序列完成时间不同，批次里就会不断出现空洞。自回归生成场景中，短序列先结束，长序列继续占着批次，新的请求只能在系统外等待，即便部分资源其实已经空出来了。

更难的是，这不只是吞吐问题，而是吞吐、延迟和内存压力同时存在的平衡问题。正在 decode 的请求希望步间延迟更低；新来的 prefill 请求希望尽快被接纳；而两者都要争抢批次槽位和 KV Cache 空间。

## 设计选择

Hetero-Paged-Infer 采用 decode 优先的连续批处理策略。调度器把请求区分为 pending、prefill 和 decode 三类状态；每次构建执行批次时，先放 decode，再用剩余容量填 prefill，只有在内存压力允许时才接纳全新的 prefill。

这是一个明确带立场的选择。系统优先保证“已经在途的请求持续前进”，而不是把新到达 prompt 的即时公平性放到第一位。同时，它把准入策略和内存压力直接耦合，而不是把批处理和 KV 分配当成彼此无关的两个子系统。

## 权衡

这样做的好处是，系统行为更像真正的 serving 引擎，而不是只会演示批次拼接的 demo。decode 优先能减少在途请求被大 prefill 拖慢的风险；内存压力门控则让过载行为变成显式策略，而不是偶然结果。

代价是，长 prompt 或大量新请求的等待时间可能更长，而且当前策略只是一个默认启发式，并不是完整的多租户公平调度框架。它优先服务于“架构清晰、行为真实”，而不是在当前阶段证明自己已经找到了所有工作负载下的最优调度。

## 当前实现状态

当前调度器实现已经会强制执行 batch size 与 token 数上限、跟踪内存压力，并通过测试覆盖混合 prefill/decode 行为。集成测试验证了：旧请求运行过程中可以接纳新工作，系统在内存压力下也能继续工作而不是直接崩溃。

但这里还没有完成的，是最终的 GPU 利用率证明。由于执行仍然通过 mock 后端完成，本页记录的是“真实存在且有正确性证据的调度策略”，而不是“已经由真实硬件吞吐结果背书的最终实现”。
